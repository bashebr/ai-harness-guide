Architecture guide

Bare Model vs. Harness

Production LLM systems split into two layers: the bare model (weights that predict tokens) and the harness (the runtime that turns predictions into reliable software). Understanding this split is the difference between a demo and a product.

Key insight: The model is a stateless function — f(context) → tokens. Everything else — memory, tools, retries, guardrails, billing, observability — lives in the harness. You own the harness; the vendor owns the weights.

Mental Model

Think of it like a web browser and a web page:

Bare model The web page

  • Static content (trained knowledge)
  • Cannot act on its own
  • Re-rendered fresh each request
  • Impressive but inert without a browser

Harness The browser

  • Runs JavaScript, fetches APIs, manages tabs
  • Enforces same-origin policy and sandboxing
  • Remembers history and bookmarks (session state)
  • Turns HTML into an interactive experience

When someone says "the AI searched the web" or "the AI ran your code," the model didn't do that — the harness intercepted a structured output, executed the action, and fed the result back into the next context window.

Architectural Distinctions

Capability Bare Model Harness / Framework
State & memory Stateless. Each call is an independent forward pass over a context array. Stateful. Persists sessions, caches, vector stores, and conversation history.
External execution Isolated inference. Cannot reach networks, filesystems, or databases. Orchestrates tool calls, sandboxes code, queries APIs, reads files.
Token management Hard context limit. Truncates or errors when input exceeds window size. Summarizes, trims, chunks, and retrieves only relevant context.
Output reliability Probabilistic text. May hallucinate structure or ignore instructions. Validates schemas, retries on failure, enforces JSON/tool formats.
Safety & access control Content filters at inference time (vendor-controlled). Your auth, rate limits, PII redaction, approval flows, audit logs.
Observability Token counts and latency from the API provider. Traces, cost attribution, evals, prompt versioning, A/B tests.
Deployment Managed endpoint or self-hosted weights (vLLM, llama.cpp). Your app server, agent loop, queue workers, or IDE integration.

Tool-Calling Loop

When an LLM needs live data or side effects, the model never executes directly. The harness runs a controlled loop:

1. User request → 2. Harness builds context → 3. Model emits tool call
4. Harness executes tool → 5. Result injected into context → 6. Model generates final answer

What the harness must handle

  • Parse — Detect tool-call tokens vs. plain text (native function calling or custom JSON blocks).
  • Authorize — Check whether this user/session may invoke that tool.
  • Execute — Run the action with timeouts, retries, and error handling.
  • Serialize — Format tool output so the model can consume it without blowing the context budget.
  • Loop — Repeat until the model returns a final answer or a max-iteration guard fires.

Rule of thumb: If it touches the outside world, it belongs in the harness — not in the prompt alone.

Who Owns What

Use this split when designing teams, on-call rotations, and SLAs:

Model team / vendor

  • Training data and fine-tunes
  • Inference latency and uptime
  • Context window size
  • Base safety filters
  • Tool-calling format support

Your harness (application) team

  • Prompt and system message design
  • Tool definitions and implementations
  • Session and memory strategy
  • Evals, regression tests, cost controls
  • User-facing reliability and UX

Minimal Python Blueprint

This skeleton shows how execution stays in application code while the model only proposes actions:

harness_loop.py 
import json

MAX_TOOL_ITERATIONS = 5

# --- Tools live in YOUR codebase, not the model ---
def fetch_weather(location: str) -> dict:
    """Mock API — replace with real HTTP call."""
    db = {"amsterdam": {"temp_c": 16, "condition": "cloudy"}}
    key = location.lower().strip()
    return db.get(key, {"temp_c": 22, "condition": "clear"})

TOOLS = {
    "fetch_weather": {
        "fn": fetch_weather,
        "description": "Get current weather for a city",
    },
}

def parse_tool_call(text: str) -> dict | None:
    """Harness validates structure before executing anything."""
    try:
        data = json.loads(text)
        if "tool" in data and data["tool"] in TOOLS:
            return data
    except json.JSONDecodeError:
        pass
    return None

def run_harness(user_prompt: str, model_client) -> str:
    messages = [
        {
            "role": "system",
            "content": (
                "Reply with JSON to call a tool: "
                '{"tool": "fetch_weather", "arg": "Amsterdam"}. '
                "Otherwise reply in plain text."
            ),
        },
        {"role": "user", "content": user_prompt},
    ]

    for _ in range(MAX_TOOL_ITERATIONS):
        response = model_client.generate(messages)
        tool_call = parse_tool_call(response)

        if not tool_call:
            return response  # Final natural-language answer

        # Execute in harness — model never runs this
        tool_fn = TOOLS[tool_call["tool"]]["fn"]
        result = tool_fn(tool_call.get("arg", ""))

        messages.append({"role": "assistant", "content": response})
        messages.append({"role": "tool", "content": json.dumps(result)})

    return "Error: max tool iterations exceeded"

Production additions: Structured logging, idempotency keys for mutating tools, human-in-the-loop approval for destructive actions, and circuit breakers when tools fail repeatedly.

Real-World Examples

Every product below wraps the same pattern — model proposes, harness disposes:

OpenAI / Anthropic APIs Model Chat completions with native tool schemas
Cursor / Copilot Harness IDE context, file edits, terminal, MCP tools
LangChain / LlamaIndex Harness Chains, agents, retrieval, memory abstractions
Claude Code / Codex CLI Harness Shell access, git, multi-step task loops
vLLM / Ollama Model Self-hosted inference servers
Custom microservice Both Your API + chosen model endpoint

Frameworks are harness accelerators — they don't replace the need to think about ownership, failure modes, and boundaries.

Decision Guide

Ask these questions before adding complexity:

Question If yes →
Does the answer need live or private data? Build harness tools (RAG, SQL, internal APIs).
Will the agent take actions (write files, send emails)? Harness must sandbox, authorize, and audit every action.
Do conversations span multiple turns? Harness owns session storage and context pruning strategy.
Is correctness more important than creativity? Harness validates outputs (JSON schema, eval gates, retries).
Is a single-shot Q&A enough? A thin API wrapper may suffice — don't over-build.

Production Checklist

Before shipping an agent to users, verify the harness covers:

  • Max iteration / cost ceiling per request
  • Timeout on every external tool call
  • Structured logs with trace IDs across model + tool steps
  • Graceful degradation when the model or a tool is down
  • Prompt and tool versioning (rollback without redeploying weights)
  • Eval suite for regressions on critical paths
  • PII handling — redact before sending to third-party APIs
  • Human approval path for irreversible operations

Anti-Patterns

Treating the prompt as the harness

"Don't make things up" in the system message doesn't stop hallucination. Validate outputs in code.

Letting the model construct SQL/shell directly

Always parameterize queries and run them through an allowlisted executor in the harness.

Unbounded agent loops

A runaway tool loop can burn budget in seconds. Set hard caps and detect repetitive failures.

Ignoring context growth

Appending full tool outputs forever silently degrades quality and doubles cost. Summarize or retrieve selectively.
